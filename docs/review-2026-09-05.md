## 按优先级排序的代码问题

P1 表示建议在面向外部用户发布前处理；P2 表示应修复的功能或可靠性问题。严重程度结合此项目浏览器模型加载器的使用场景判断。

### 1. P1：固定输出缓冲区掩盖了真实 DEFLATE 解压量

位置：[src/format/zip.ts:214](../src/format/zip.ts#L214)，以及之后的长度与 CRC 校验。

`inflateSync(compressed, { out: new Uint8Array(uncompressedSize) })` 不保证超出输出缓冲区时抛错。当前安装的 fflate 仍执行解压循环，超出 TypedArray 的写入被丢弃，返回结果被限制在缓冲区长度内。因此对 `bytes.byteLength` 的校验不能证明实际流长度符合声明，CRC 也只是对截断内容进行计算。

本次用约 1,147 字节的 ZIP，实际 DEFLATE 内容为 1 MiB 的 `A`，将声明长度改为 1 字节，并填写单字节 `A` 的 CRC；即使配置 `maxEntryBytes=1`、`maxTotalBytes=1`，解析仍成功，返回 1 字节。

影响：无效归档被接受；恶意压缩流可以绕过声明解压量预算而消耗大量 CPU。固定缓冲区约束了输出分配，**这里没有证据表明发生了越界内存访问或任意代码执行**。默认 Worker 可降低主线程阻塞，但不能免除 CPU 消耗；禁用 Worker 时会直接阻塞主线程。

建议：采用能报告并限制实际产出量的增量解压路径，每块输出检查累计量，越限立即停止，同时验证准确的最终长度。增加“真实展开量大于声明值、CRC 对截断前缀有效”的回归用例，不能只检查 ZIP 头声明值。

### 2. P1：下载和 ZIP 体积上限不约束图片解码内存

位置：[src/loader/SOGLoader.ts:189](../src/loader/SOGLoader.ts#L189)、[src/format/image.ts:88](../src/format/image.ts#L88)、[src/format/meta.ts:182](../src/format/meta.ts#L182)。

所有属性图并行解码之后，才验证维度是否相同以及 `count <= width * height`。没有最大宽高、像素数、总解码字节预算，也没有把实际纹理尺寸与渲染设备限制联动。低熵 PNG / WebP 的压缩文件很小，解码结果却可能很大，500 万 splat 限制无法阻止 `count=1` 配上巨幅纹理。

安全模拟：自定义 decoder 返回 5 张 16384×16384 的图像描述，`count=1` 的资源仍进入 `ready`；对应 RGBA 总量为 5 GiB。这里只模拟维度，**没有真实分配 5 GiB 图片或使浏览器崩溃**。代码中的原生解码路径同样没有事前像素预算。

建议：读取图片头部并在解码前检查尺寸与累计解码预算；对 decoder 返回值再做防御校验；限制同时解码的图片数量；prepare 前检查设备纹理尺寸与资源预算。应有可配置的 `maxDecodedBytes` / `maxImagePixels`，不能仅依赖压缩字节数。

### 3. P1：WebGL 排序较慢时，持续运动会导致所有结果被丢弃

位置：[src/render/sort/WebGLSortBackend.ts:145](../src/render/sort/WebGLSortBackend.ts#L145)。

每次相机变化都会递增 generation，Worker 完成后只要结果不是最新 generation 就直接丢弃。当相机更新比 Worker 快时，每个结果都“过期”，上传永远追不上；渲染继续使用旧顺序，透明混合错误。

确定性模拟：10 次视角更新、5 次排序完成，上传次数为 0。真实浏览器也复现：Tomatoes 的 445,409 个 splat 在 forced WebGL 持续转动约 3 秒，显示 60 FPS，但 `totalSortCount` 始终为 2，排序更新为 0/s。Lion 较小，在本机可保持约 60 次/s，所以现有小模型运动用例未发现问题。

建议：对同一有效资源允许应用单调更新的最近完成结果，同时继续计算最新待处理视角。资源销毁/替换的失效标识应与相机更新编号分离。增加 Worker 每次耗时跨越多个帧的持续运动测试；性能监控同时记录完成、丢弃和上传次数。

### 4. P2：缓存路径在叠加 SH 前截断 DC 颜色，改变渲染结果

位置：[src/render/SOGWebGPUCache.ts:243](../src/render/SOGWebGPUCache.ts#L243)，`packColor()` 在该文件第 48 行，SH 累加在第 324 行附近；对照 [src/render/material.ts:152](../src/render/material.ts#L152)。

缓存先把基础颜色夹到 [0,1] 并量化到 8 bit，再叠加 SH。非缓存路径先叠加全部 SH，最后再夹取。两者不等价。例如基础颜色 1.4、SH 贡献 -0.5，正确顺序得到 0.9，提前夹取后得到约 0.5。

这不是仅靠极端伪造数据才能触发：本次读取真实码本，Lion 的基础颜色范围约为 [-0.330, 1.440]，Tomatoes 为 [-0.440, 1.440]。它们分别有 77 / 82 个码本值处于 [0,1] 外。此处已确认公式不一致及真实码本触发条件，但没有逐像素量化整个模型的误差。

建议：保留未截断的 DC 系数或足够范围的浮点基础颜色，全部 SH 求值后再量化最终颜色。加入超范围 DC 与相反符号 SH 相抵消的基准，以及缓存 / 非缓存跨路径比较；两个各自生成的截图基线不能证明等价。

### 5. P2：取消图片解码时遗漏 ImageBitmap.close()

位置：[src/format/image.ts:99](../src/format/image.ts#L99)。

`createImageBitmap()` 完成后先检查 abort，再构造关闭函数；如果 decode 尚未完成时已取消，返回的 bitmap 在检查处被丢弃，没有执行 `close()`，也没有转交给 loader 的清理栈。

模拟异步解码返回前取消：得到 `ABORTED`，`close()` 调用次数为 0。反复切换大模型会让本应及时释放的原生图像资源依赖后续 GC 回收。

建议：在局部保存 bitmap 所有权，遇到取消或后续异常先 close 再抛错；针对解码尚未完成、完成边界及 Worker 回退路径测试资源关闭次数。

### 6. P2：异步中心读回期间留下临时 render target

位置：[src/render/centers.ts:95](../src/render/centers.ts#L95)。

设置临时目标并渲染后，等待 `readRenderTargetPixelsAsync()` 完成才在 finally 恢复。等待期间，应用的动画循环或另一个 prepare 可以使用同一个 renderer，把画面画进临时纹理，甚至影响尚未提交完成的操作。保存 previous 也发生在前面的异步 compile 之前，存在恢复过时状态的可能。

Mock renderer 复现：读回 Promise 未完成时，当前目标仍为 `sog-center-readback`，原目标为 null；完成后才恢复。

建议：把 `setRenderTarget → quad.render → restore` 限定在不含 await 的同步区间；根据 Three.js 读回 API 的目标参数显式异步读取指定 target。覆盖“动画循环继续运行时加载第二个资源”及并发准备测试。

### 7. P2：有限 JSON 数值可能在解码后变为 Infinity / NaN

位置：[src/format/meta.ts:207](../src/format/meta.ts#L207)，以及 scale codebook 的指数转换。

当前只验证输入是有限 Number，没有验证 `expm1()`、`exp()`、Float32 转换或缓存中的 Float16 打包后仍可表示。`means.maxs=[1000,1000,1000]` 已被 loader 接受为 ready，bounds.max 却变成三个 Infinity，后续包围体、排序和投影都会失去意义。

建议：对解码后数值进行有限性与表示范围验证；为位置、尺度及缓存量化分别明确可支持范围，必要时回退到不量化的路径。增加有限输入导致指数溢出的测试。

### 8. P2：干净目录直接 npm pack 可生成没有入口代码的包

位置：[package.json:23](../package.json#L23)。

`dist/` 被 Git 忽略，包导出仅指向 dist，但没有 prepack / prepublishOnly 构建与校验。外部包测试自己先构建，掩盖了正常打包时的缺失。在包含当前 manifest、README 和许可证但不含 dist 的隔离目录执行 npm pack dry-run，成功生成清单，但没有任何 dist 文件，导出入口不存在。

建议：增加 prepack 构建与产物存在性检查，并明确 release 工作流。保留真实消费者验证，但升级到浏览器从发布 tarball 加载模型、启动 Worker 并完成 prepare/render。此问题针对 npm 发布流程，不是 GitHub 推送限制。

### ZIP 校验是一个明确可优化的加载热点

[src/format/zip.ts:60](../src/format/zip.ts#L60) 采用每字节 8 次位循环计算 CRC。Moon 在浏览器中的 ZIP 阶段约 2.39 秒，远大于该次本地下载的 75 ms 和解码的 229 ms。

另外在 Node 对相同 67,214,485 字节输入做单次对照：现有同构位循环 CRC 用时约 1764 ms，256 项查表 CRC 用时约 119 ms，两者 checksum 均为 409164617。**CRC 微基准约 14.8 倍差距，不代表完整加载可提速 14.8 倍**。优先使用正确性经过验证的查表/分块 CRC，同时保留校验和越限中断。

### 公网加载不能使用 localhost 数据宣传

Moon 压缩包为 67.21 MB（64.1 MiB）。仅按有效带宽计算，10 Mbps 的纯传输理论下限约 53.8 秒，50 Mbps 约 10.8 秒，100 Mbps 约 5.4 秒；还没计入 RTT、服务器、JS、解码和准备。当前没有 range、渐进显示、分块、LOD，这属于已声明的 MVP 范围限制，却明显制约大场景的首屏体验。

建议为真实模型补充生产构建的冷/热缓存、带宽/延迟受限条件，以及下载、解码、prepare、首次实际显示的独立数据。分块和 LOD 可以留到后续版本，但必须明确 500 万上限是数量/内存护栏，而不是实时性能承诺。

这些不是完整进程或峰值内存测量。还存在浏览器图片、下载 chunks 与合并缓冲、Blob、Worker 复制、驱动和 framebuffer 开销。GPU 数字与 CPU 数字不能当作互相替代的两种统计。

当前单一资源超过 100 万 splat 就禁用投影缓存，贡献剔除也随之关闭；25 份 Lion 的逻辑实例批量仍可走缓存，493 万个唯一点的 Moon 却不走。两类“约 500 万”性能不能互相代表。未来宜基于显存预算、SH 和可见比例决定缓存，并研究不依赖全量投影缓存的剔除。

### Worker 和每帧成本

- 每个资源为 5–7 张图片分别新建模块 Worker；主线程提前创建备用 Blob，Worker 路径又复制图片 bytes。可考虑复用少量 Worker、控制并发并按需创建回退 Blob，先验证低内存设备收益。
- 排序 Worker 引入 `Matrix4` from `three/webgpu`，示例生产构建产生约 220.93 kB 的独立排序 Worker。仅使用深度矩阵元素时，可以移除该 Worker 对整个 Three.js 入口的需求。
- [sort.worker.ts:29](../src/workers/sort.worker.ts#L29) 虽回收传输结果，但 `createDepthKeys` 和 radix 仍每次分配约 5 个 count 长度的 32 位数组，约 20N 字节临时数组/排序，尚未包含输出复制；44.5 万点约 8.9 MB/次。宜复用 key、index、scratch，不只回收最终结果。
- 本次构建共享主 JS chunk 约 941.58 kB，gzip 261.85 kB，包含 Three.js 与库；不能全算成此库的体积。构建后 npm tarball 在加入本报告前约 113 kB，解包 526 kB，未包含大型模型。
